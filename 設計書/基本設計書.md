## 基本設計書の位置づけ

本書は、要件定義書(第3版)で定めた要件を基に、「気象・イベント連動 AI需要予測＆自動発注アシスタント」のシステム構成を定める基本設計書である(作成責任者: 伊藤久喜)。API・テーブル・画面・予測ロジックの詳細は詳細設計書(作成責任者: 矢澤秀都)で定める。

設計手法は、プロジェクト計画書に定められた Papyrus(Eclipse Papyrus)を用いたモデルベースでのシステム構成設計とする。本書のシステム構成・機能構成を Papyrus でモデル化し、別途管理する。

## システム構成

```
事務所PC(ブラウザ) ⇔ 画面(React) ⇔ 本体API(FastAPI) ⇔ DB(PostgreSQL)
                                        ├─ 提案作成処理(最新性判定→気象→予測→提案)
                                        ├─ 予測モデル(ファイル。未接続時はベースライン)
                                        └─ 気象API(Open-Meteo)
モデル作成用プロジェクト(学習・評価・バックテスト) ──モデルファイル+評価レポート──▶ 本体
サンプルデータ生成(F-20) ──標準取込形式CSV・真の需要──▶ 本体 / モデル作成用プロジェクト
```

画面・本体API・DBの3層構成とする。担当者は事務所PCのブラウザから画面を操作し、画面は REST API(JSON)で本体を呼び出す。本体は画面が開かれたときに提案の最新性を判定し、必要なら気象予報の取得・需要予測・発注数/製造数の計算を行って提案を保存する。

本体の内部は、次の部品に分け、それぞれ単独でテストできるようにする。

| 部品 | 役割 |
|---|---|
| 取込 | 標準取込形式のCSV(商品マスタ・POS・在庫・廃棄)の検証・保存、取込履歴 |
| 特徴量作成 | 予測モデルの入力となる特徴量の表を作る(曜日・祝日・特売・気象・過去実績) |
| 予測 | モデルファイルの読み込みと推論。未接続・不適合などの場合はベースライン(前週同曜日)で予測 |
| 発注計算 | 予測値・在庫・発注残・発注単位から、生鮮の発注数と惣菜の製造数を計算 |
| 提案・承認 | 提案の作成・再計算・修正・承認・取消と状態管理、最新性の判定 |
| 認証 | ログイン、役割と所属部門による権限 |
| 気象クライアント | 気象APIの呼び出しと結果の保存(差し替え可能) |

**予測モデルの分離**: 予測モデルは本体から切り離し、インターフェース定義(入力の特徴量の表、出力の予測販売数、付随情報)に沿ったモデルファイルを本体が読み込む。モデルの学習・評価は本体とは別の「モデル作成用プロジェクト」で行い、成果物(モデルファイル+評価レポート)だけを本体に渡す。インターフェース定義の詳細は詳細設計書に示す。

### 評価環境(AWS)

研究室のAWS環境に EC2 を1台用意し、ローカル開発環境と同じ構成(Docker Compose)で配置する。DBも同じサーバーのコンテナに置き、RDS は使わない(構成を単純にするため)。外部からのアクセスは HTTPS とし、アクセス元を研究室・協力店舗に限定する。

> **【確認事項】** EC2 のインスタンス種別と、アクセス元の具体的な制限方法(IPアドレス制限等)は、評価対象の店舗が決まった段階で確定する。

## 機能構成と処理の流れ

### 事前準備: モデルの作成

1. 取込済みデータ(またはサンプルデータ)から学習用の表を作る。
2. 候補アルゴリズム(ランダムフォレスト、勾配ブースティング)で学習する。
3. 時系列で分割した検証期間で WAPE・MAE を算出し、ベースライン(前週同曜日)と比較する。ベースラインを下回るモデルは採用しない。
4. バックテストで、提案通りに発注・製造した場合の廃棄数・欠品数をベースラインと比較する。
5. 採用モデルをファイルとして保存し、評価レポートとともに本体へ渡す。

これらはモデル作成用プロジェクトで、手動のコマンドとして実行する(例: 週1回)。

### データ取込

担当者が画面から標準取込形式のCSVをアップロードする独立した操作とする(提案作成処理の中では取り込まない)。取込のたびに件数・エラー行の履歴を残し、不正な行はスキップして報告する(取込全体は止めない)。同じデータを再取込した場合は、POS・廃棄は「日付×商品」、在庫は「基準日時×商品」の単位で上書きする。在庫は画面からの手入力もできる。

### 提案の作成・再計算

1. 担当者が発注画面・製造計画画面を開くと、既存の提案をすぐに表示する。
2. 本体が提案の最新性を判定する。未承認かつ人が修正していない提案について、未作成・在庫/POS/発注残の更新・特売/カレンダーの変更・モデルの版の変更・気象予報の取得からの経過(既定3時間)のいずれかに当てはまれば、裏で再計算する。
3. 再計算は「最新性判定 → 気象取得 → 予測 → 提案作成」の順に行い、対象20品で1分以内に終える。実行中は進捗を表示し、完了後に画面の提案を差し替える。
4. 同じ「部門×対象日」(生鮮の既定表示では「部門×発注日」)の処理が実行中であれば待ち、最新であれば再実行しない(二重実行防止)。
5. 人が修正した提案・承認済みの提案・承認を取り消した提案は自動では数量を変えず、再計算した値を差分として表示する。担当者が採用すると、新しい提案値に置き換わる。
6. 画面には予測作成・予報取得・在庫基準の各日時を鮮度として表示する。

担当者は再計算ボタンで手動で再計算することもできる(最新性判定を省略して部門の全提案を再計算し、保護される提案は差分として表示する)。対象日は、生鮮は商品ごとにその時点で発注できる最も早い納品日(リードタイムと発注締め時刻から算出)とし、リードタイムの異なる商品も1画面に並べる。惣菜は翌日(当日朝は当日)とする。いずれも当日〜15日先に限る。

### 確認・修正・承認

- 数量の修正は未承認の提案のみ可能で、修正理由(天候判断/特売・売場都合/在庫差異/その他)を必須とし、修正前の値を残す。
- 承認は個別、または一括で行う。警告付きの提案は一括承認の対象外とする。
- 承認済みの提案は期限(生鮮: 部門別の発注締め時刻、惣菜: 時間帯ごとの製造開始時刻)までは取り消せる。期限を過ぎた承認済みの提案は「確定」となり、生鮮では発注残として以後の計算に使う。期限までに承認されなかった提案は「期限切れ」として記録に残す。

### 欠損時の扱い

既定値で黙って計算を続けることはせず、欠損ごとに次のように扱う。

| 欠損 | 計算方法 | 表示・承認 |
|---|---|---|
| 在庫が無い(生鮮のみ。当日分の取込も手入力も無し) | 持越見込0で計算 | 「在庫未取込」警告。一括承認の対象外、個別承認時に確認ダイアログ |
| 販売実績が無い(新商品など) | 予測値0 | 「販売実績なし」警告。一括承認の対象外 |
| 気象予報が取得できない | ベースラインで予測 | 「気象データなし(ベースライン予測)」警告。一括承認の対象外 |
| 前日分のPOSが無い | 確定している最新日までで特徴量を作る | 「POS未更新」警告 |
| モデル未接続・不適合・時間帯区切りの不一致 | ベースラインで予測 | 「ベースライン予測」表示(警告ではない) |

惣菜は前日作成時に陳列残数0で計算するのが正規の手順のため、陳列残数の欠損による警告は付けない。

## データ設計方針

### 取込データ(標準取込形式)

店舗データの入手見込みは未定のため、本システム側で標準取込形式(CSV)を定める。実データ・サンプルデータとも同じ入口から取り込み、実データ入手時は変換スクリプトを用意して差し替える。列の詳細は詳細設計書に示す。

| データ | 主な項目 | 頻度 |
|---|---|---|
| 商品マスタ | 商品コード・名称・部門・発注単位(入数)・リードタイム・持越可否・原価・売価(任意) | 変更時 |
| POS売上実績 | 日付・時刻(または時間帯)・商品コード・販売数 | 日次 |
| 在庫 | 基準日時・商品コード・在庫数 | 発注前 |
| 廃棄実績 | 日付・商品コード・廃棄数 | 日次 |

予測単位(日別/時間帯別)は商品マスタに持たず、部門から決める。

### システム内で管理するデータ

祝日・行事日カレンダー、特売・チラシ、気象(予報・実績、取得日時つき)、予測結果(モデル版・使用した特徴量)、発注提案/製造計画(根拠のスナップショット・修正理由・修正前の値・承認履歴・警告)、利用者・所属部門、設定、取込履歴を管理する。

テーブルは次の通りとする(項目は詳細設計書で定義する)。

departments, users, user_departments, products, pos_sales, inventory_snapshots, waste_records, display_stock_entries, weather_forecasts, weather_actuals, calendar_days, promotions, forecasts, proposals, proposal_histories, proposal_jobs, import_logs, settings

- 発注残は、状態「確定」かつ納品日が未到来の提案から導出し、専用のテーブルは作らない。
- 提案は作成時点の根拠(在庫・気象・特徴量)をスナップショットとして保持し、元データが上書きされても承認済み提案の根拠は変わらないようにする。

## 外部連携・インターフェース設計方針

- **画面⇔本体**: REST API(JSON)。認証、データ取込、在庫・陳列残数の入力、特売・カレンダー、提案(一覧・再計算・修正・承認・一括承認・取消・再計算値の採用)、承認済み発注リスト、設定、商品一覧、予測と実績の比較(Should)を提供する。API仕様は詳細設計書に示し、Swagger UI でも参照できる。
- **気象データAPI**: Open-Meteo(無料・APIキー不要)を採用する。店舗の緯度・経度を指定して予報と過去実績を取得し、取得日時とともに保存する。予報の提供範囲(約16日先)のため、対象日は当日〜15日先に限る。タイムアウトは10秒。呼び出し処理は1つの部品に閉じ込め、差し替え可能にする。
- **POS・在庫データ**: 標準取込形式のCSVを担当者がアップロードする。店舗システムの出力形式が分かった段階で変換スクリプトを用意する。
- **既存発注システム**: 今回は連携しない。承認済み発注リスト(F-13)を見て担当者が入力する暫定運用とし、連携先確定後にファイル出力(F-19)を検討する。

> **【確認事項】** 学習用の過去気象で降水確率が得られるか(Open-Meteo の過去実績API/過去予報API)を確認する。得られない場合は降水量を特徴量とする。

## セキュリティ設計方針

本システムは店舗の機密情報(詳細POSデータ・在庫・仕入れ情報)を扱う可能性があるため、以下の方針とする。

- ID・パスワードによるログインを必須とし、パスワードはハッシュ化して保存する。
- 役割(担当者/店長)と所属部門により操作できる範囲を制限する(要件定義書「利用者と権限」参照)。他部門の提案の修正・承認はできない。
- 評価環境(AWS)では HTTPS を用い、アクセス元を研究室・協力店舗に限定する。本体APIを呼び出せる Web オリジンは設定で限定する(CORS)。
- 店舗からのデータ提供は、事前に店舗と合意した範囲に限定する。データが得られない場合は研究用サンプルデータで代替する。
- 実データは研究室のAWS環境内でのみ管理し、外部への持ち出しは行わない。実データ・接続情報などの設定・学習済みモデルはリポジトリに含めない。
- 決済情報(カード情報等)は扱わない。

## 運用・保守設計方針

インサイトレポートが示す通り、現場スタッフはAI自動発注に対し「信用できない」「慣れない」といった心理的障壁を持ちやすい(要件定義書 リスク4)。このため、運用は以下の方針とする。

- **スモールスタート評価**: 全店舗一括ではなく、協力が得られた特定部門・店舗で評価を始める。プロトタイプ完成後に、模擬評価(研究室メンバー)、バックテスト、スモールスタート評価(協力店舗スタッフ)を行い、結果を提案書に反映する。
- **人間による最終確認**: 提案は担当者が根拠・鮮度・警告を確認し、承認してから扱う。完全自動化ではなく「不確実性からの解放(安心感)」を体現する位置づけとする。
- **修正履歴の活用**: 修正理由と修正前後の値を記録し、予測精度の評価やモデル改善の材料とする。
- **モデルの更新**: 新しい実績がたまったらモデル作成用プロジェクトでモデルを再作成し(例: 週1回、手動コマンド)、評価レポートでベースラインを上回ることを確認してから本体のモデルファイルを差し替える。予測結果にはモデルの版を記録する。
- **稼働監視**: 稼働確認用のエンドポイント(/health)を用意する。提案作成処理が失敗した場合は画面に表示し、担当者が手動で再実行できる。
- **DB構造の管理**: Alembic のマイグレーションでDB構造の変更を管理する。

> **【確認事項】** 評価対象の部門・店舗と、モデルの再作成の頻度は、現場協力の得られ方に応じて確定する。

## 今後の進め方

詳細設計書で、予測モデルのインターフェース定義・特徴量、発注数・製造数の計算式、提案の状態遷移、API・画面・テーブル・標準取込形式の詳細を定める。

実装は「生鮮の日別発注 → 惣菜の時間帯別製造計画」の順に段階的に進め、各段階で動作する状態を保つ。3文書の確定日程とシステムプロトタイプ以降の期限は、指導教員と調整のうえ再設定する。
