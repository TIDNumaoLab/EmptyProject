## 1. 目的と方針

### 1.1 背景
第2版の3文書は、試作(`prototype/`)の実装内容に合わせて改訂されたため、「作るべきシステム(To-Be)」ではなく「試作の実装説明」になっている。試作の暫定値(5商品・4時間帯・安全係数1.1 等)と本来の要件が区別できず、インサイトワークレポートとの対応(イベント連動、廃棄ロス削減)や数値化された成功基準も欠けている。

### 1.2 改訂の狙い(4点すべて対象)
1. To-Be仕様への書き直し(試作の実装状況を本文から外す)
2. インサイトとの整合(潜在ニーズ → 要件 → 機能 → 評価指標のトレース)
3. 業務モデルの実態合わせ(部門別の発注・製造業務、在庫、イベント)
4. 成功基準の数値化と未確定事項の方針決定

### 1.3 方針(案A)
- 3文書構成(要件定義書・基本設計書・詳細設計書)と各文書の作成責任者・期限は維持する。
- 本文はTo-Be仕様として記述する。試作の実装状況・ファイルパス・試作固有の挙動は本文から外し、各文書末尾の付録「試作(prototype)からの変更点」に集約する。
- `prototype/` は試作として扱い、本改訂ではコードを変更しない。
- 未確定事項は「仮の前提(設計はこれで進める)+ヒアリング確認項目」の形で記述し、設計を止めない。

## 2. 業務モデル(To-Be)

### 2.1 利用者
| 利用者 | 役割 |
|---|---|
| 発注担当者(部門担当社員) | 提案の確認・修正・承認、特売登録、在庫の手入力 |
| 店長 | 承認状況の確認、設定の管理、利用者管理 |

利用端末は事務所PCのブラウザのみ。ログインして承認者を記録する。

### 2.2 部門別の業務
| | 生鮮(青果・鮮魚) | 惣菜 |
|---|---|---|
| 業務 | 仕入発注 | 製造計画 |
| 決めるもの | 納品日の発注数量(日単位) | 対象日の時間帯別製造数 |
| 予測単位 | 日別販売数 | 時間帯別販売数(時間帯の区切りは設定) |
| 在庫の扱い | 発注時点の在庫から納品日までの持越見込を差し引く | 陳列残数を差し引く |
| 作成タイミング(仮の前提) | 発注を行うとき(ヒアリング情報では前日の閉店間際が多い) | 前日に作成し、当日朝に陳列残数・最新予報で再計算(未確認。ヒアリング項目) |

リードタイムは商品ごとに設定する(既定1日)。

### 2.3 業務フロー(生鮮の例)
1. 担当者が発注画面を開く。
2. システムが提案の最新性を判定し、必要なら自動で作成・再計算する(取込 → 気象取得 → 予測 → 提案作成。§5.4)。
3. 担当者は商品ごとに、提案数・予測値・根拠(天候・気温・降水確率、祝日/行事日・特売、前週同曜日の実績、現在庫)と、予測の鮮度表示を確認する。
4. 必要なら数量を修正し、修正理由(天候判断/特売・売場都合/在庫差異/その他)を選ぶ。
5. 個別承認または一括承認する。発注締め時刻までは承認を取り消せる。
6. 承認済み発注リスト(画面・印刷)を見て、既存の発注システム・PDAへ入力する(連携先確定までの暫定運用)。

### 2.4 イベント
- 祝日・行事日(連休、年末年始、土用の丑の日など): カレンダーデータとして事前に用意する(祝日は公開データ、行事日は手動登録)。
- 特売・チラシ: 担当者が画面から登録する(商品・期間・内容)。
- 地域イベント: 優先度低(Could)。

### 2.5 対象外
値引き判断、次世代ESL、ウェアラブル・ストアコントローラー、決済情報、地域イベント(将来候補)、既存発注システムとの直接連携。

## 4. データ・外部連携

### 4.1 標準取込形式
店舗データの入手見込みは未定のため、本システム側で標準取込形式(CSV)を定める。実データ・サンプルデータとも同じ入口から取り込み、実データ入手時は変換スクリプトを1本用意して差し替える。

| データ | 主な項目 | 頻度 | 実データが無い場合 |
|---|---|---|---|
| 商品マスタ | 商品コード・名称・部門・予測単位(日/時間帯)・発注単位(入数)・リードタイム・持越可否 | 変更時 | サンプルマスタ(生鮮・惣菜で10〜20品程度) |
| POS売上実績 | 日付・時刻(または時間帯)・商品コード・販売数 | 日次 | サンプル生成(天候・曜日・祝日・特売の効果を再現) |
| 在庫 | 基準日時・商品コード・在庫数 | 発注前 | サンプル生成、または画面で手入力 |
| 廃棄実績 | 日付・商品コード・廃棄数 | 日次 | サンプル生成(評価用。Should) |

列の詳細定義は詳細設計書に記す。

### 4.2 システム内で管理するデータ
祝日・行事日カレンダー、特売・チラシ、気象(予報・実績、取得日時つき)、予測結果(モデル版・使用した特徴量)、発注提案/製造計画(根拠・修正理由・承認履歴・警告)、利用者、設定、取込履歴。

### 4.3 取込の扱い
- 取込のたびに履歴(件数・エラー行)を残す。
- 不正な行はスキップして報告し、取込全体は止めない。
- 同じ期間のデータを再取込した場合は上書きする。

### 4.4 外部連携
- 気象: Open-Meteo を継続採用。呼び出し部分は差し替え可能にする。取得結果は取得日時とともに保存し、根拠表示と再学習に使う。取得できない場合は提案に「気象データなし」の警告を付ける(既定値で黙って続行しない)。
- 既存発注システム: 今回は連携しない(F-19 で将来対応)。

## 5. 予測・発注ロジック

### 5.1 予測モデル
- 2つのモデルを持つ: 日別モデル(生鮮: 商品×日)、時間帯別モデル(惣菜: 商品×日×時間帯)。商品ごとではなく全商品で1モデルとし、商品コードを特徴量に含める。
- 特徴量: 商品、曜日、祝日・行事日フラグ、連休の何日目か、特売フラグ、天候区分、気温、降水確率(時間帯別モデルはその時間帯の値)、前週同曜日の実績、直近7日平均。
- 前週同曜日・直近7日平均は、予測対象日より前に確定したデータ(前日までのPOS)だけから作る。
- アルゴリズム候補: ランダムフォレスト(scikit-learn)、勾配ブースティング(LightGBM 等)。

### 5.2 モデルの作成と評価(F-09)
1. 取込済みデータ(またはサンプル)から学習用の表を作る。
2. 候補アルゴリズムで学習する。
3. 時系列で分割し、直近4週間を検証期間として MAE・MAPE を算出する。雨天日・祝日に絞った誤差も出す。
4. ベースライン(前週同曜日の実績)と比較する。ベースラインを下回るモデルは採用しない。
5. 採用モデルをファイルに保存し、版番号・学習期間・評価結果を評価レポートとして出力する。
6. 新しい実績がたまったら再作成する(例: 週1回、手動コマンド)。

学習・評価は本体とは別の「モデル作成用プロジェクト/ノートブック」で行い、成果物(モデルファイル+評価レポート)だけを本体に渡す。

### 5.3 モデルの接続(モデルファイル方式)
- 予測モデルは本体から切り離し、インターフェース定義に沿ったモデルファイルを本体が読み込む。
- インターフェース定義: 入力=§5.1 の特徴量の表(列名・型・意味を詳細設計書で定義)、出力=行ごとの予測販売数(0以上の小数)、付随情報=版番号・学習期間・評価結果。
- モデルは Python(本体と同じバージョン・ライブラリ)で作成する。
- ベースライン(前週同曜日)を同じインターフェースで本体に組み込み、モデル未接続時の代替とする。
- モデルの適合はインターフェース適合テストで確認する。

### 5.4 提案の作成・再計算(F-08)
- 発注画面を開いたとき、未承認の提案について次のいずれかに当てはまれば自動で作成・再計算する:
  1. 未作成
  2. 作成後に在庫・POSが新しく取り込まれた
  3. 使用した気象予報の取得から一定時間(F-17、既定3時間)が経過した
- 対象日: その時点で発注できる最も早い納品日を、商品ごとのリードタイムと発注締め時刻(F-17)から算出する(生鮮)。惣菜は対象日の時間帯別計画とする。
- 処理順: 取込 → 気象取得 → 予測 → 提案作成。対象20品で1分以内。実行中は進捗を表示する。
- 二重実行防止: 同じ対象の処理が実行中・作成済み(最新)の場合は再実行しない。
- 承認済みの提案は再計算しない(人の判断を上書きしない)。未承認の既存提案は上書きし、同じ対象の提案を重複させない。
- 手動での再計算もできる。
- 画面に鮮度を表示する(例: 予測作成 10/16 19:42、予報取得 19:40、在庫 19:30時点)。
- 気象・在庫が取得できない場合も提案は作成し、「在庫未取込」等の警告を付けて目立つように表示する。

### 5.5 発注数・製造数の計算
生鮮:
```
持越見込 = max(0, 現在庫 − 納品日までの残り販売見込)   ※持越不可の商品は0
必要数   = 納品日の予測需要 × 安全係数(部門別、既定1.1)
発注数   = 発注単位で切り上げ( max(0, 必要数 − 持越見込) )
```
例: 予測需要42.3、安全係数1.1、持越見込8、入数6 → 46.53 − 8 = 38.53 → 42

惣菜:
```
製造数 = 切り上げ( max(0, 時間帯予測 × 安全係数 − 陳列残数) )
```
対象日全時間帯の計画を作成し、陳列残数を入力すると以降の時間帯を再計算できる。

### 5.6 提案の状態
未承認 → 承認済み。承認済みは発注締め時刻まで取消可能(取消すと未承認に戻る)。数量修正は未承認のみ。修正時は修正理由を必須とし、修正前の提案値を保持する。

## 6. 成功基準・評価方法

目標値は仮値(指導教員との合意・現場ヒアリングで確定)。

| 指標 | 測り方 | 目標値(仮) | 実データが無い場合 |
|---|---|---|---|
| 予測精度 | 評価レポート(§5.2)。直近4週間のMAPE | ベースライン比でMAPE 20%以上改善。雨天日・祝日でも改善 | サンプルデータで評価し「参考値」と明記 |
| 発注作業時間 | 模擬課題(1部門・10商品の発注判断)で現行方法と本システムの所要時間を計測 | 50%削減 | 研究室メンバーや協力スタッフ数名で模擬評価 |
| 廃棄ロス・欠品 | バックテスト(提案通り発注した場合の廃棄数・欠品数をベースラインと比較) | 廃棄数10%削減、欠品数は増やさない | サンプルデータでシミュレーション |
| 心理的負担 | 利用前後のアンケート(5段階: 発注への不安、提案への信頼、使いやすさ) | 不安・信頼が平均1ポイント改善 | 模擬評価の参加者で実施 |
| (補助)提案採用率 | 修正なしで承認された提案の割合 | 70%以上 | 模擬評価のログから算出 |

### 6.1 トレーサビリティ(骨子)
| 潜在ニーズ(インサイトレポート) | 機能 | 指標 |
|---|---|---|
| 「プレッシャー」と「責任」からの解放 | F-07/08 自動提案、F-10 根拠表示、F-12 人による最終承認 | 心理的負担、提案採用率 |
| 「本来の自分たちの役割」を取り戻す | F-08 自動作成、F-12 一括承認 | 発注作業時間 |
| 店舗の「コントロール感」を取り戻す | F-10 根拠(天気・イベント・在庫)と鮮度を1画面で把握 | 心理的負担(信頼) |
| 経営課題(廃棄ロス・機会ロス) | F-03 在庫連携、F-08 発注計算 | 廃棄ロス・欠品 |

### 6.2 評価スケジュール
12/18 のプロトタイプ完成後、12月下旬〜1月上旬に模擬評価とバックテストを行い、1/15 の提案書に反映する。

## 7. システム構成・非機能

### 7.1 構成
```
事務所PC(ブラウザ) ⇔ 画面(React) ⇔ 本体API(FastAPI) ⇔ DB(PostgreSQL)
                                        ├─ 提案作成処理(取込→気象→予測→提案)
                                        ├─ 予測モデル(ファイル。未接続時はベースライン)
                                        └─ 気象API(Open-Meteo)
モデル作成用プロジェクト(学習・評価) ──モデルファイル+評価レポート──▶ 本体
```
- 技術は試作と同じ(Python/FastAPI/SQLAlchemy/Alembic、React/TypeScript/Vite、PostgreSQL、Docker)。
- 本体の内部は 取込 / 特徴量作成 / 予測 / 発注計算 / 承認 / 認証 の部品に分け、それぞれ単独でテストできるようにする。
- 定時バッチは持たない。提案の作成は §5.4 の発注画面起点の処理と手動再計算で行う。
- 配置: 開発はローカル(Docker Compose)。評価時は研究室AWSのEC2 1台に同じ構成で配置し、DBも同サーバーのコンテナに置く(RDSは使わない)。

### 7.2 非機能要件
| 項目 | 方針 |
|---|---|
| 性能 | 画面表示2秒以内。提案作成処理は対象20品で1分以内 |
| 可用性 | 評価期間中に安定稼働。処理が失敗した場合は画面に表示し、手動で再実行できる |
| セキュリティ | ID・パスワードによるログイン(パスワードはハッシュ化して保存)、担当者/店長の権限、AWS上ではHTTPS、アクセス元を研究室・協力店舗に限定 |
| データ管理 | 実データは研究室AWS内のみに置き、リポジトリに含めない。店舗と合意した範囲のみ扱う |
| 保守性 | 設定は環境変数と設定画面(F-17)で管理。DB構造の変更はAlembicのマイグレーションで管理 |
| 利用環境 | 事務所PCのブラウザ(Chrome/Edge 最新版)、画面幅1280px以上 |
| テスト | 発注計算・取込・状態遷移・提案作成処理は自動テスト。モデルはインターフェース適合テスト |

## 8. ヒアリング確認項目
設計は以下を仮の前提として進め、ヒアリング結果で確定する。

| 項目 | 仮の前提 |
|---|---|
| 発注を行うタイミング | 不定(前日の閉店間際が多いと聞いている)。タイミングに依存しない設計とする |
| 惣菜の製造計画の作成タイミング | 前日作成+当日朝に再計算 |
| 発注締め時刻 | 設定値(閉店時刻を既定) |
| 納品の頻度・リードタイム | 毎日納品、リードタイム1日 |
| 持越の可否 | 商品マスタで指定(鮮魚・惣菜は持越不可を既定) |
| 発注単位(ケース入数) | 商品マスタで指定 |
| 店舗POSから出力できる形式 | 標準取込形式へ変換スクリプトで対応 |
| 在庫を把握・出力できるタイミング | 発注前に出力できない場合は画面で手入力 |
| 惣菜の時間帯の区切り | 設定値(例: 開店〜11時、11〜14時、14〜17時、17時〜閉店) |
| 評価指標の目標値 | §6 の仮値 |

### 9.1 試作からの主な変更点(付録の骨子)
- 予測の手動1件実行 → 発注画面起点の自動作成・再計算(最新性判定つき)
- 時間帯別の一律予測 → 部門別(生鮮=日別発注、惣菜=時間帯別製造計画)
- 一律の安全係数のみ → 在庫(持越見込・陳列残数)・発注単位を考慮した計算式、部門別安全係数
- イベント未対応 → 祝日・行事日、特売・チラシを特徴量に追加
- 予測モデルを本体に内蔵 → モデルファイル方式で分離し、ベースラインを代替として内蔵
- 既定値での黙った続行 → 警告表示
- 同一対象の提案重複 → 未承認は上書き
- 修正フラグのみ → 修正理由と修正前の値を記録
- 承認のみ → 一括承認、承認者記録、締め時刻までの取消
- 認証なし → ログインと権限
- 1時間天気画面 → 根拠表示に統合
- 固定5商品・4時間帯 → 商品マスタ取込、時間帯は設定
