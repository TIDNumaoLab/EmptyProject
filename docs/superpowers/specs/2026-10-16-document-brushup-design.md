## 1. 目的と方針

### 1.1 背景
第2版の3文書は、試作(`prototype/`)の実装内容に合わせて改訂されたため、「作るべきシステム(To-Be)」ではなく「試作の実装説明」になっている。試作の暫定値(5商品・4時間帯・安全係数1.1 等)と本来の要件が区別できず、インサイトワークレポートとの対応(イベント連動、廃棄ロス削減)や数値化された成功基準も欠けている。

### 1.2 改訂の狙い(4点すべて対象)
1. To-Be仕様への書き直し(試作の実装状況を本文から外す)
2. インサイトとの整合(潜在ニーズ → 業務要件 → 機能 → 評価指標のトレース)
3. 業務モデルの実態合わせ(部門別の発注・製造業務、在庫、イベント)
4. 成功基準の数値化と未確定事項の方針決定

### 1.3 方針(案A)
- 3文書構成(要件定義書・基本設計書・詳細設計書)と各文書の作成責任者は維持する。期限は §10 の通り再調整する。
- 本文はTo-Be仕様として記述する。試作の実装状況・ファイルパス・試作固有の挙動は本文から外し、各文書末尾の付録「試作(prototype)からの変更点」に集約する。
- `prototype/` は試作として扱い、本改訂ではコードを変更しない。
- 未確定事項は「仮の前提(設計はこれで進める)+ヒアリング確認項目」の形で記述し、設計を止めない。
- 設計手法はプロジェクト計画書の定め通り Papyrus(Eclipse Papyrus)によるモデルベース設計を継続する。
- 日時はすべて日本時間(Asia/Tokyo)で扱う。

### 2.2 部門別の業務

### 2.4 業務フロー(生鮮の例)
1. 担当者が(必要なら)POS・在庫のCSVを取り込むか、在庫を画面で入力する。
2. 担当者が発注画面を開く。既存の提案をすぐに表示し、最新性判定で必要と判断されれば裏で再計算して差し替える(§5.4)。
3. 担当者は商品ごとに、提案数・予測値・根拠(天候・気温・降水確率、祝日/行事日・特売、前週同曜日の実績、在庫・発注残)と鮮度表示・警告を確認する。
4. 必要なら数量を修正し、修正理由(天候判断/特売・売場都合/在庫差異/その他)を選ぶ。
5. 個別承認、または一括承認する(警告付きの提案は一括承認の対象外)。発注締め時刻までは承認を取り消せる。
6. 承認済み発注リスト(画面・印刷)を見て、既存の発注システム・PDAへ入力する(連携先確定までの暫定運用)。

惣菜は、前日に翌日の時間帯別計画を作成・承認し、当日朝に陳列残数を入力して、製造開始時刻前の時間帯を見直す。

### 2.5 イベント
- 祝日・行事日(連休、年末年始、土用の丑の日など): 祝日は公開データ(内閣府の祝日CSV等)を初期取込し、行事日は店長が登録する。
- 特売・チラシ: 担当者が画面から登録する(商品・期間・内容)。
- 地域イベント: 今回は実装しない。将来候補(F-18、Could)とする。

### 2.6 対象外
値引き判断、次世代ESL(価格表示ミス・クレームの課題はESL施策の領域)、ウェアラブル・ストアコントローラー、決済情報、既存発注システムとの直接連携、相場(市場価格)の予測への反映(データ入手が困難なため。将来候補)。

## 4. データ・外部連携

### 4.1 標準取込形式
店舗データの入手見込みは未定のため、本システム側で標準取込形式(CSV)を定める。実データ・サンプルデータとも同じ入口(担当者のアップロード)から取り込み、実データ入手時は変換スクリプトを1本用意して差し替える。

| データ | 主な項目 | 頻度 | 実データが無い場合 |
|---|---|---|---|
| 商品マスタ | 商品コード・名称・部門・発注単位(入数)・リードタイム・持越可否・原価・売価(任意) | 変更時 | サンプルマスタ(生鮮・惣菜で10〜20品程度) |
| POS売上実績 | 日付・時刻(または時間帯)・商品コード・販売数 | 日次 | F-20 で生成 |
| 在庫 | 基準日時・商品コード・在庫数 | 発注前 | F-20 で生成、または画面で手入力 |
| 廃棄実績 | 日付・商品コード・廃棄数 | 日次 | F-20 で生成(評価用) |

予測単位は商品マスタに持たず、部門から決める。列の詳細定義は詳細設計書に記す。

### 4.2 システム内で管理するデータ
祝日・行事日カレンダー、特売・チラシ、気象(予報・実績、取得日時つき)、予測結果(モデル版・使用した特徴量)、発注提案/製造計画(根拠のスナップショット・修正理由・修正前の値・承認履歴・警告)、発注残(承認済みで未納品の発注)、利用者・所属部門、設定、取込履歴。

### 4.3 取込の扱い
- 取込は担当者がCSVをアップロードする独立した操作とし、提案作成処理(§5.4)の中では行わない。
- 取込のたびに履歴(件数・エラー行)を残す。不正な行はスキップして報告し、取込全体は止めない。
- 再取込時の上書き単位: POS・廃棄は「日付×商品」、在庫は「基準日時×商品」。
- 提案は作成時点の根拠(在庫・気象・特徴量)をスナップショットとして保持するため、元データが上書きされても承認済み提案の根拠は変わらない。
- サーバー側で入力を検証する(未登録の商品コード、予報範囲外の日付、型・範囲の不正)。

### 4.4 外部連携
- 気象: Open-Meteo を継続採用。呼び出し部分は差し替え可能にする。予報の提供範囲(約16日先)のため、対象日は当日〜15日先に制限する。タイムアウトは10秒。取得結果は取得日時とともに保存し、根拠表示と再学習に使う。
- 学習用の過去気象で降水確率が得られるかは要確認(§8)。得られない場合は降水確率に代えて降水量を特徴量とし、予測時も予報の降水量を使う。
- 既存発注システム: 今回は連携しない(F-19 で将来対応)。
- 稼働確認用に /health エンドポイントを設ける。

### 4.5 研究用サンプルデータ生成(F-20)
実データが得られない間の開発・動作確認・バックテスト用に、次を再現した擬似データを生成する。
- 曜日・天候(雨天で約8割)・気温・祝日/行事日・特売による需要の変動、惣菜の時間帯別構成
- 「真の需要」と、在庫制約下で実際に売れた数(欠品時は打ち切り)、欠品数、廃棄数、在庫
- 期間は1年以上(祝日・行事日・季節を含めるため)。乱数シードを固定し再現可能にする
- 出力は標準取込形式(§4.1)と、評価用の真の需要ファイル

## 5. 予測・発注ロジック

### 5.1 予測モデル
- 2つのモデルを持つ: 日別モデル(生鮮: 商品×日)、時間帯別モデル(惣菜: 商品×日×時間帯)。商品ごとではなく全商品で1モデルとし、商品コードを特徴量に含める。
- 特徴量: 商品、曜日、祝日・行事日フラグ、連休の何日目か、特売フラグ、天候区分、気温、降水確率(または降水量。§4.4)、前週同曜日の実績、直近7日平均。時間帯別モデルでは気象・前週同曜日・直近7日平均を時間帯単位で作る。
- 日別モデルの気象の集約: 天候区分=営業時間中の代表天候(降水ありを優先した最頻値)、気温=最高気温、降水確率=営業時間中の最大値。詳細は詳細設計書で定める。
- 情報の時点: 実績系の特徴量は「発注時点で確定しているデータ」だけから作る。生鮮は発注日の前日までのPOS(リードタイム1日なら対象日の2日前まで)、惣菜は計画作成日の前日までのPOS。学習データも同じずれ幅で作り、学習時と運用時の条件を揃える。
- アルゴリズム候補: ランダムフォレスト(scikit-learn)、勾配ブースティング(LightGBM 等)。

### 5.2 モデルの作成と評価(F-09)
1. 取込済みデータ(またはサンプル)から学習用の表を作る。
2. 候補アルゴリズムで学習する。
3. 時系列で分割し、直近の検証期間で WAPE(=Σ|誤差|/Σ実績)と MAE を算出する。販売数0の行があっても計算できる WAPE を主指標とする。
4. 雨天日・祝日/行事日に絞った誤差も、該当日数を併記して出す(日数が少ない場合は参考扱い)。
5. ベースライン(前週同曜日の実績)と比較する。ベースラインを下回るモデルは採用しない。
6. バックテスト: 検証期間について、「モデル予測+§5.5の計算」と「ベースライン(前週同曜日)+同じ§5.5の計算」で発注・製造した場合の廃棄数・欠品数(原価・売価があれば金額換算)を比較する。需要にはサンプルでは真の需要を使う。実データでは欠品時に販売数が打ち切られる点を制約として明記する。
7. 採用モデルをファイルに保存し、版番号・学習期間・時間帯の区切り・評価結果を評価レポートとして出力する。
8. 新しい実績がたまったら再作成する(例: 週1回、手動コマンド)。

学習・評価は本体とは別の「モデル作成用プロジェクト/ノートブック」で行い、成果物(モデルファイル+評価レポート)だけを本体に渡す。

### 5.3 モデルの接続(モデルファイル方式)
- 予測モデルは本体から切り離し、インターフェース定義に沿ったモデルファイルを本体が読み込む。
- インターフェース定義: 入力=§5.1 の特徴量の表(列名・型・意味を詳細設計書で定義)、出力=行ごとの予測販売数(0以上の小数)、付随情報=版番号・学習期間・時間帯の区切り・評価結果。
- モデルは Python 3.11(本体と同じバージョン・ライブラリ)で作成する。
- ベースライン(前週同曜日)を同じインターフェースで本体に組み込み、次の場合の代替とする: モデル未接続、モデルファイルがインターフェースに適合しない、時間帯別モデルの時間帯の区切りが現在の設定と異なる(このときは再学習が必要と表示する)、気象データが得られない。
- モデルの適合はインターフェース適合テストで確認する。

### 5.4 提案の作成・再計算(F-08)
- きっかけ: 担当者が発注画面・製造計画画面を開いたとき(自動)、または再計算ボタン(手動)。
- 画面は既存の提案をすぐに表示し、再計算が必要な場合は裏で実行して完了後に差し替える。実行中は進捗を表示する。
- 自動再計算の対象: 状態が「未承認」かつ人が修正していない提案で、次のいずれかに当てはまるもの。
  1. 未作成
  2. 作成後に在庫・POS・発注残が更新された
  3. 作成後に特売・カレンダーが変更された
  4. 作成後にモデルの版が変わった
  5. 使用した気象予報の取得から一定時間(F-17、既定3時間)が経過した
- 人が修正した未承認の提案、承認済みの提案、承認を取り消した提案は自動では数量を変えない。再計算した新しい提案値を差分として表示し、担当者が採用するかを選ぶ(採用すると未承認・未修正の提案に戻る)。
- 対象日: 生鮮は、その時点で発注できる最も早い納品日を商品ごとのリードタイムと部門の発注締め時刻から算出する。惣菜は翌日(当日朝は当日)の時間帯別計画とする。対象日は当日〜15日先に限る。
- 処理順: 最新性判定 → 気象取得 → 予測 → 提案作成。対象20品で1分以内。
- 二重実行防止: 「部門×対象日」単位で、実行中のものがあれば待ち、最新のものがあれば再実行しない。
- 画面に鮮度を表示する(例: 予測作成 10/16 19:42、予報取得 19:40、在庫 19:30時点)。

### 5.5 発注数・製造数の計算
生鮮:
```
販売見込 = 在庫基準日時から納品時刻までの予測販売数
         = 基準日の残り分(日別予測 × 残り営業時間の売上構成比)+ 途中の日の日別予測
持越見込 = max(0, 在庫数(基準日時) + 発注残(納品日より前に届く承認済み発注) − 販売見込)
           ※持越不可の商品は0
必要数   = カバー期間(納品日〜次回納品日の前日。毎日納品なら納品日1日)の予測需要 × 安全係数(部門別、既定1.1)
発注数   = 発注単位で切り上げ( max(0, 必要数 − 持越見込) )
```
- 売上構成比は過去POSの時間帯別の売上比率から求める(時刻つきPOSが無い場合は営業時間の比率で代用)。
- 仮の前提(リードタイム1日・毎日納品・納品は開店前)では途中の日は無く、販売見込は基準日の残り分だけになる。
- 例: 納品日の予測需要42.3、安全係数1.1、持越見込8、入数6 → 46.53 − 8 = 38.53 → 42
- 発注単位への丸めは切り上げを既定とし、端数の扱い(一定割合未満は切り捨て等)はヒアリング項目とする(§8)。

惣菜:
```
製造数(時間帯 t) = 切り上げ( max(0, 時間帯 t の予測 × 安全係数 − 陳列残数(t)) )
陳列残数(t) = 入力時刻の直後の時間帯のみ、入力された陳列残数。それ以外の時間帯は0
```
- 前日作成時は陳列残数を0として全時間帯を計算する。当日朝などに陳列残数を入力すると、製造開始時刻前の時間帯を再計算する(承認済みの時間帯は差分表示。§5.4)。
- 前の時間帯の製造残を次の時間帯に繰り越す計算は行わない(簡略化。陳列残数の入力で補正する)。

### 5.6 欠損時の扱い
| 欠損 | 計算方法 | 表示・承認 |
|---|---|---|
| 在庫が無い(取込も手入力も無し) | 持越見込0(生鮮)/陳列残数0(惣菜)で計算 | 「在庫未取込」警告。一括承認の対象外、個別承認時に確認ダイアログ |
| 気象予報が取得できない | ベースラインで予測 | 「気象データなし(ベースライン予測)」警告。一括承認の対象外 |
| 前日分のPOSが無い | 確定している最新日までで特徴量を作る | 「POS未更新」警告 |
| モデル未接続・不適合・時間帯区切りの不一致 | ベースラインで予測 | 「ベースライン予測」表示(警告ではない) |

既定値で黙って計算を続けることはしない。

### 5.7 提案の状態
| 状態 | 意味 | 遷移 |
|---|---|---|
| 未承認 | 作成済み。修正の有無を「修正あり」フラグで持つ | 承認 → 承認済み。期限経過 → 期限切れ |
| 承認済み | 担当者・店長が承認 | 期限前の取消 → 未承認(修正ありとして扱い、自動再計算しない)。期限経過 → 確定 |
| 確定 | 期限(生鮮: 発注締め時刻、惣菜: 時間帯の製造開始時刻)を過ぎた承認済み。生鮮は発注残になる | 変更不可 |
| 期限切れ | 期限までに承認されなかった提案 | 変更不可(記録として残す) |

- 数量修正は未承認のみ可能。修正理由を必須とし、修正前の提案値を保持する。
- 再計算の差分を採用した場合は、修正前の値・修正理由の履歴を残したうえで新しい提案値に置き換える。

## 6. 成功基準・評価方法

目標値は仮値(指導教員との合意・現場ヒアリングで確定)。目標の達成判定は実データ・現場スタッフでの評価で行い、サンプルデータ・研究室メンバーでの結果は「仕組みの動作確認・操作性の参考」と位置づけて判定には使わない。

| 指標 | 測り方 | 目標値(仮) | 実データ・現場協力が無い場合 |
|---|---|---|---|
| 予測精度 | 評価レポート(§5.2)。検証期間の WAPE | ベースライン比で WAPE 20%以上改善。雨天日・祝日も改善(日数を併記) | サンプルで動作確認のみ(判定しない) |
| 発注作業時間 | 模擬課題(1部門・10商品の発注判断)で、現行方法(過去実績表と天気予報だけを渡して手で判断)と本システムの所要時間を計測 | 50%削減 | 研究室メンバーで実施し操作性の参考とする |
| 廃棄ロス・欠品 | バックテスト(§5.2-6)。原価・売価があれば金額換算(経営層向け試算) | 廃棄数10%削減、欠品数は増やさない | サンプル(真の需要あり)でシミュレーションし、参考値とする |
| 心理的負担 | 協力店舗スタッフによる利用前後アンケート(5段階: 発注への不安、提案への信頼、使いやすさ)とインタビュー | 不安・信頼が平均1ポイント改善 | 使いやすさのみ研究室メンバーで参考評価 |
| (補助)提案採用率 | 現場スタッフが修正なしで承認した提案の割合 | 70%以上 | 指標としない |

## 7. システム構成・非機能

### 7.1 構成
```
事務所PC(ブラウザ) ⇔ 画面(React) ⇔ 本体API(FastAPI) ⇔ DB(PostgreSQL)
                                        ├─ 提案作成処理(最新性判定→気象→予測→提案)
                                        ├─ 予測モデル(ファイル。未接続時はベースライン)
                                        └─ 気象API(Open-Meteo)
モデル作成用プロジェクト(学習・評価・バックテスト) ──モデルファイル+評価レポート──▶ 本体
サンプルデータ生成(F-20) ──標準取込形式CSV・真の需要──▶ 本体 / モデル作成用プロジェクト
```
- 技術は試作と同じ(Python 3.11/FastAPI/SQLAlchemy/Alembic、React/TypeScript/Vite、PostgreSQL、Docker)。開発端末とDockerイメージのPythonバージョンを3.11に揃える。
- 本体の内部は 取込 / 特徴量作成 / 予測 / 発注計算 / 提案・承認 / 認証 の部品に分け、それぞれ単独でテストできるようにする。
- 定時バッチは持たない。提案の作成は §5.4 の画面起点の処理と手動再計算で行う。
- 配置: 開発はローカル(Docker Compose)。評価時は研究室AWSのEC2 1台に同じ構成で配置し、DBも同サーバーのコンテナに置く(RDSは使わない)。

### 7.2 非機能要件
| 項目 | 方針 |
|---|---|
| 性能 | 画面表示(既存提案の表示)は2秒以内。提案作成処理は対象20品で1分以内(裏で実行し完了後に差し替え) |
| 可用性 | 評価期間中に安定稼働。処理が失敗した場合は画面に表示し、手動で再実行できる。/health で稼働確認 |
| セキュリティ | ID・パスワードによるログイン(パスワードはハッシュ化して保存)、役割と所属部門による権限(§2.1)、AWS上ではHTTPS、アクセス元を研究室・協力店舗に限定、CORSで呼び出し元を限定 |
| データ管理 | 実データは研究室AWS内のみに置き、リポジトリに含めない。店舗と合意した範囲のみ扱う |
| 保守性 | 設定は環境変数と設定画面(F-17)で管理。DB構造の変更はAlembicのマイグレーションで管理 |
| 利用環境 | 事務所PCのブラウザ(Chrome/Edge 最新版)、画面幅1280px以上 |
| テスト | 発注・製造数の計算、取込、状態遷移、最新性判定、欠損時の扱い、権限は自動テスト。気象APIは模擬応答でテスト。モデルはインターフェース適合テスト |

## 8. ヒアリング・確認項目
設計は以下を仮の前提として進め、ヒアリング・調査の結果で確定する。

| 項目 | 仮の前提 |
|---|---|
| 発注を行うタイミング | 不定(前日の閉店間際が多いと聞いている)。タイミングに依存しない設計とする |
| 発注締め時刻 | 部門別の設定値(既定は閉店時刻)。仕入先単位で異なるかを確認 |
| 納品の頻度・リードタイム・納品時刻 | 毎日納品、リードタイム1日、納品は開店前 |
| 持越の可否 | 商品マスタで指定(鮮魚・惣菜は持越不可を既定) |
| 発注単位(ケース入数)と端数の丸め方 | 商品マスタで指定。丸めは切り上げ |
| 惣菜の製造計画の作成タイミング | 前日作成+当日朝に再計算 |
| 惣菜の時間帯の区切りと製造開始時刻 | 設定値(例: 開店〜11時、11〜14時、14〜17時、17時〜閉店。製造開始は各時間帯の1時間前) |
| 店舗POSから出力できる形式・時刻の粒度 | 標準取込形式へ変換スクリプトで対応 |
| 在庫を把握・出力できるタイミング | 発注前に出力できない場合は画面で手入力 |
| 原価・売価の提供可否 | 任意項目。無ければ数量のみで評価 |
| 学習用の過去気象で降水確率が得られるか(Open-Meteo の過去実績API/過去予報API) | 得られなければ降水量に置き換え |
| 評価指標の目標値 | §6 の仮値 |
| 現場評価(スモールスタート)の可否・対象部門 | 協力が得られた部門で実施 |
